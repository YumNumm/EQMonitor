# 変更リスクに応じたテスト方針

## 原則

- TDD や Widget Test をすべての変更へ一律に適用しない。
- TDD（テスト駆動開発）は必須ではない。テストを先に書くことや RED → GREEN の証跡は要求せず、実装後に必要なテストを追加してよい。
- ユーザーの指示と、誤動作時の影響・回帰可能性に応じてテスト方法を選ぶ。
- 文言や情報配置だけの軽微な変更では、関連する既存テストと静的解析による確認を選択できる。
- 緊急情報の判定、データ変換、状態遷移、通知条件、永続化、障害修正には自動テストを追加する。
- TDD の任意性は、必要な自動テストや回帰確認を省略できるという意味ではない。
- 過去の計画にある TDD 手順は当時の作業記録として扱い、新しい作業へ一律に引き継がない。現在のユーザー指示と本方針で検証方法を決める。

## テストを追加しない場合

アプリコードの変更では、作業結果に理由を記載し、少なくとも変更機能の既存テストと変更対象の静的解析を実行する。

```bash
cd app
mise exec -- flutter test test/feature/<feature> --dart-define=CI=true
mise exec -- flutter analyze lib/feature/<feature>
```

ドキュメントのみの変更ではアプリのテスト追加や実行を必須とせず、リンク先の存在、記述と現行設定の整合、差分、適用対象の Markdown lint を確認する。
