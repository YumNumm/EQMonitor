# HTTPキャッシュ適用範囲のオプトイン化 設計

## 背景

現在の共通 `dioProvider` は `HttpCacheInterceptor` を持つため、同じ
`ApiClient` を通るすべての GET 200レスポンスをETagの有無にかかわらず
永続保存する。キャッシュキーにクエリ文字列が含まれるのでレスポンス同士は
衝突しないが、pagingのcursor、検索条件付き地震履歴、ユーザー固有情報、
Realtime ticketなども保存対象になっている。

HTTPキャッシュの目的は、Home画面や個別ページを開いた際に、明示的に選んだ
レスポンスを即時表示して初期表示を高速化することである。paging、検索、
ユーザー固有情報、短命なリアルタイム情報の保存は目的に含めない。

## ゴール

- HTTPキャッシュを明示的なオプトイン方式に変更する。
- 通常のGETはキャッシュせず、選定済みの非paging GETだけを保存する。
- cache-first表示とETagによるバックグラウンド再検証を対象画面で維持する。
- 旧バージョンが広範囲に保存したHTTPキャッシュを安全に消去する。
- キャッシュが利用不能でも、ネットワークから画面を表示できるようにする。

## 対象範囲

HTTPキャッシュを許可するのは次のGETだけとする。

- `/v1/start`
- `/v1/changelog`
- パラメータのmanifestと本体
- 全都道府県の過去最大震度
- 指定都道府県の市区町村別過去最大震度
- 地震詳細 `/v2/earthquake/{eventId}`
- 電文詳細 `/v2/telegram/eventId/{eventId}/details`
- Feed個別詳細 `/v2/feeds/source/{telegramHash}`
- 地震活動GeoJSON。外部ホスト専用Dioによる既存キャッシュを維持する

次は明示的に対象外とする。

- Feed一覧。Home内の一覧とFeedページの初回ページを含む
- 地震履歴一覧、条件検索、地域別検索
- EEW履歴一覧
- 津波履歴、通知履歴など、その他のpaging API
- cursor、page、またはpaging目的のlimitを使うすべてのAPI
- 端末情報、通知設定、購読状態などのユーザー固有API
- Realtime ticket、最新EEWなどの短命・リアルタイムAPI
- 今後追加され、キャッシュ利用を明示していないGET

## アーキテクチャ

### 通常APIクライアント

共通の通常クライアントから `HttpCacheInterceptor` を外す。App Check、端末ID、
端末認証、通信ログ、タイムアウト、ベースURL、共通ヘッダは維持する。paging、
検索、ユーザー固有API、Realtime APIを含む通常の通信はこのクライアントを使う。

### キャッシュ対応APIクライアント

通常クライアントと同じ接続設定および認証系インターセプタを持つ専用Dioと
`ApiClient` を追加し、ここにだけ `HttpCacheInterceptor` を登録する。対象範囲で
列挙したcache-first providerの再検証だけが、このクライアントを利用する。

新しいAPIは通常クライアントを使うのが既定となる。キャッシュ対象を増やす場合は、
レスポンスの性質を確認して対象範囲を更新し、providerをキャッシュ対応クライアントへ
明示的に接続する。

### cache-firstデータフロー

1. キャッシュ専用読み出しクライアントから保存済みレスポンスを読み、即時表示する。
2. キャッシュ対応クライアントでバックグラウンド再検証する。
3. ETagが一致した304は保存済みbodyから200相当のレスポンスへ復元する。
4. 200の新しいレスポンスは保存し、画面の値を更新する。
5. キャッシュmissまたは破損時は、キャッシュ対応クライアントで完全取得する。

`CachedNotifier` の通常再検証とforce-freshはキャッシュ対応クライアントを使う。
Feed一覧の `CachedNotifier` とpaging用 `cacheFirstRefresh` は撤去し、初回ページを
含むすべてのページを通常クライアントから取得する。

## 既存キャッシュの移行

旧キャッシュには対象外となるレスポンスが保存されている可能性があるため、変更後の
初回起動でHTTPキャッシュDBを全消去する。専用の整数移行バージョンを
`SharedPreferencesKey` で管理し、現在値が必要バージョン未満の場合だけ次を行う。

1. キャッシュDBを開く。
2. 全エントリを削除する。
3. 削除が成功した後に移行バージョンを保存する。

削除完了前にcache-only読み出しを開始しない。削除に失敗した場合は移行済みとせず、
その起動ではHTTPキャッシュを使わずにネットワーク通信へ縮退する。次回起動時に移行を
再試行する。

## キャッシュ無効化とエラー処理

- デバッグ設定でHTTPキャッシュを無効化した場合、読み出し、保存、
  `If-None-Match` 送信、304復元をすべて停止する。
- キャッシュmissまたは破損時は完全取得へ切り替える。
- キャッシュDBを開けない場合はキャッシュなしの通信へ縮退し、画面表示を妨げない。
- バックグラウンド再検証の失敗時は既存のcache-first状態管理に従う。
- 地震詳細では、キャッシュよりRealtime upsert/deleteとデバッグoverrideを優先する。
- 固定値や生成データによるフォールバックは追加しない。

## テスト

### クライアント境界

- 通常Dioに `HttpCacheInterceptor` が存在しないこと。
- キャッシュ対応Dioに `HttpCacheInterceptor` が1個だけ存在すること。
- 両Dioが必要な接続設定と認証系インターセプタを持つこと。
- HTTPキャッシュ無効化中は読み書きと条件付きリクエストを行わないこと。

### 適用範囲

- 対象providerが「キャッシュ即表示、背景再検証、最新値への更新」を行うこと。
- Feed一覧とpaging DataSourceがcache-onlyクライアントを使用しないこと。
- cursor付き一覧、検索条件付き地震履歴、ユーザー固有GET、Realtime GETを通常
  クライアントで取得してもHTTPキャッシュDBへエントリが作成されないこと。
- 地震活動GeoJSONの専用Dioにキャッシュ以外のアプリAPI用インターセプタが混入しないこと。

### 移行と既存保証

- 旧エントリが移行時にすべて削除されること。
- 移行完了後の次回起動では再削除しないこと。
- 削除失敗時は旧キャッシュを表示せず、次回起動で再試行すること。
- ETag保存、`If-None-Match` 再送、304復元、200更新、破損復旧の既存テストを維持すること。
- 地震詳細でRealtime更新がstale cacheより優先される既存テストを維持すること。

## 対象外

- サーバーやCloudflare側のキャッシュポリシー変更
- HTTPキャッシュのTTL導入
- pagingデータ向けの別ストレージキャッシュ導入
- キャッシュ対象画面の追加
- デバッグ用HTTPキャッシュ一覧画面のUI変更
