# テーマライブラリと共有機能

## 背景

`AppTheme` は `light` と `dark` の両方の `ThemeColorSet` を持てるモデルとして
定義されているが、保存層とエディタ層がその意図を守っていない。

`AppThemeNotifier` は `app_theme_light` と `app_theme_dark` という2つの
SharedPreferences キーに `AppTheme` を丸ごと保存し、それぞれ片側の
`ThemeColorSet` しか読まない。1つのテーマが持つ light/dark のペアという構造が、
保存の時点で2つに分断されている。

さらに `ThemeEditorController._save` は編集対象モードの `ThemeColorSet` だけを
持つ `AppTheme` を組み立て、反対側のモードを `null` で保存する。名前も
`'カスタム'` で固定的に上書きされる。結果として、ライト用テーマを1色でも編集
すると、そのテーマが持っていたダーク面の定義とユーザーが付けた名前が失われる。

テーマを複数管理したい、テーマごとに名前を付けたい、ライトとダークを統合して
扱いたいという要求は、いずれもこの分断を解消することそのものである。
Deep Link によるインポートも、テーマが「light と dark を併せ持つ1つの単位」
として同一性を持たない限り、受け取ったものをどこへ入れるかが定まらない。

## 方針

テーマの保存単位を「light と dark の両方を必ず持つ1つのテーマ」に統一し、
それを並べたライブラリを単一のキーで永続化する。

`ThemeColorSet` を light/dark 両方について必須にすることで、統合管理が型で
保証される。片側欠落を実行時に補う必要がなくなるため、`AppTheme.colorSetFor`
の null フォールバックと `modes` フィールドは不要になり削除する。

テーマの選択はライブラリ全体に対して1つとする。ライト表示とダーク表示で別の
テーマを選ぶ手段は提供しない。どの明度で描画するかは既存の `themeMode`
（light / dark / system）設定が決め、テーマ選択とは直交した関心事として扱う。

## データモデル

`theme_library` という単一の SharedPreferences キーに以下を保存する。

```
ThemeLibrary
  version         スキーマバージョン
  selectedThemeId 選択中テーマの id
  themes          List<UserTheme>（表示順を保持する）

UserTheme
  id        アプリ内で一意な識別子
  name      ユーザーが編集できる表示名
  light     ThemeColorSet（必須）
  dark      ThemeColorSet（必須）
  origin    ThemeOrigin
  updatedAt 最終更新時刻

ThemeOrigin（sealed）
  Builtin(presetId)                    ビルトインプリセット。編集不可
  Custom(basePresetId?)                ユーザーが作成したテーマ
  Imported(shareId, importedAt, author) Deep Link 由来のスナップショット
```

`Builtin` は `themes` に永続化しない。プリセットは
`themePresetsProvider` が返すコード上の定義を正本とし、ライブラリと連結して
一覧に表示する。プリセットの定義がアプリ更新で変わったときに、保存済みの
古いコピーが残り続けることを避けるためである。

`selectedThemeId` はプリセットの id も指しうる。

### 保有上限

ユーザーが保有できるテーマは `Custom` と `Imported` を合わせて3つまでとする。
`Builtin` はこの上限に数えない。プリセットは常に選択可能な別枠として扱い、
ユーザーが自作テーマを作る余地をプリセットの個数に左右されないようにする。

上限に達している状態で作成またはインポートを試みた場合は、置き換える対象を
ユーザーに選ばせるか、操作を中断させる。暗黙に古いテーマを溢れさせない。

### 色の表現

色の JSON 表現は既存の `ColorJsonConverter` を変更せずに用いる。不透明な色は
`#RRGGBB`、半透明を含む色は `#AARRGGBB` で表現する。震度色の前景は
`IntensityTextColor` のタグ付きユニオン（`{"type":"auto"}` または
`{"type":"manual","color":"#RRGGBB"}`）を維持する。

既にクリップボード経由でユーザーがエクスポートした JSON が存在するため、
フィールド名と色の表現は互換性を保つ。

## マイグレーション

`app_theme_light` と `app_theme_dark` から `theme_library` へ移行する。

両キーが同一のテーマを指している場合は1つの `UserTheme` に統合する。
異なるテーマを指している場合は、`app_theme_light` の light 面と
`app_theme_dark` の dark 面を組み合わせた1つの `UserTheme` を作る。
これはユーザーが実際に画面で見ていた配色をそのまま保持する唯一の合成であり、
どちらか一方を捨てる案は採らない。

移行後のテーマ名は、両キーが同名ならその名前を、異なるなら light 側の名前を
引き継ぐ。`'カスタム'` に潰されていた名前はそのまま残るため、ユーザーが後から
改名できることをもって足りるとする。

新形式の保存が完了してから旧キーを削除する。途中でプロセスが終了した場合は
旧キーが残るため次回起動で再試行され、冪等に振る舞う。これは
`ThemeMigration.migrateFromLegacyIntensityColors` が既に採用している順序で
あり、同じ規律を踏襲する。

`theme_library` が既に存在する場合はマイグレーションを試行しない。

## 編集モデル

エディタは対象テーマのドラフトをメモリ上に持ち、明示的な保存操作で
ライブラリへ書き戻す。未保存の変更を残して画面を離れようとした場合は破棄の
確認を出す。1色変更するたびに永続化する現在の挙動は、複数テーマを持つと
「試している最中の状態」が確定状態と区別できなくなるため採らない。

エディタ内では light と dark をセグメントで切り替え、同一テーマの両面を
行き来する。片面の値をもう片面へ複製する操作を用意する。

`Builtin` のテーマを編集しようとした場合は、複製して編集するかを確認し、
複製した `Custom` テーマに対して編集を開始する。プリセット自体は変更しない。
このとき上限に達していれば、複製する前に上限の扱いを解決する。

## Deep Link によるインポート

### 経路の分離

`NotificationDeepLink` は、通知の `link` フィールドと OS のディープリンクで
同一の許可リストを共用している。流入経路によって開ける画面が変わると契約が
二重化するため、という意図がコメントとして明記されている。

テーマインポートはこの共用に含めない。テーマはアプリ全体の配色を置き換える
ため、サーバーからのプッシュ通知を経由して到達できる経路を作らない。
OS のディープリンク専用の判定として、既存の許可リストとは別に実装する。

### 受信時の挙動

受信時は必ず確認画面を表示する。テーマ名、作者名、light と dark の
プレビュー、震度色のサンプルを提示し、ユーザーが追加を選んだときだけ
ライブラリへ加える。無言で適用しない。

インポートしたテーマは受信時点のスナップショットとして保存する。公開元が
後から更新または削除されても、手元のテーマは影響を受けない。

コールドスタートは `AppLinksColdStartGate` と `splash_page` が既に持つ
pending consume のパターンに載せる。

### 取得元

テーマ本体はリンクに埋め込まず、バックエンドから `shareId` で取得する。
ペイロードの型はバックエンドの Valibot スキーマを正本とし、OpenAPI を経由して
`packages/eqmonitor_api` の Dart クライアントとして生成されたものを使う。
アプリ側で共有ペイロードの型を独自に定義しない。

生成された型と `ThemeColorSet` の相互変換は明示的なマッパーとして書く。
`ThemeColorSet` はアプリ内部の表現であり、API 契約に直接結び付けない。

公開が停止されたテーマを取得した場合は、削除された旨を表示して追加しない。

## 前提となる未整備の基盤

Universal Links / App Links の検証ファイルがどこにも配信されていない。

`AndroidManifest.xml` は `deeplink.eqmonitor.app` に対して
`autoVerify="true"` を指定しているが、
`https://deeplink.eqmonitor.app/.well-known/assetlinks.json` が存在しない。
`Runner.entitlements` は `applinks:deeplink.eqmonitor.app` を宣言しているが、
`apple-app-site-association` が存在しない。リポジトリ内に当該ドメインを
配信する構成も見当たらない。

現状では https のディープリンクは検証に失敗し、アプリではなくブラウザで開く。
テーマ共有はこのドメイン配信基盤の整備を前提とする。基盤側の設計は
eqmonitor-backend の
`docs/superpowers/specs/2026-08-19-theme-sharing-api-design.md` で扱う。

Android には `eqmonitor://` スキームの intent-filter が無く、iOS の
`Info.plist` にのみ登録されている。共有リンクは https のみで設計し、
カスタムスキームを共有経路に使わない。

## 対象範囲

- `ThemeLibrary` モデルと単一キーへの永続化
- `app_theme_light` / `app_theme_dark` からのマイグレーション
- テーマ一覧画面（選択、作成、複製、改名、削除、並べ替え）
- ドラフト方式のエディタと light / dark の切り替え
- Deep Link 受信とインポート確認画面
- 共有ペイロードと `ThemeColorSet` のマッパー

以下は対象外とする。

- 共有リンクの発行（バックエンド API の実装が前提）
- ドメイン配信基盤の構築
- テーマの公開一覧やギャラリー
- `ThemeColorSet` のフィールド追加・削除

## テスト

マイグレーションについて、旧2キーが同一テーマの場合、異なるテーマの場合、
片方のみ存在する場合、どちらも存在しない場合、`theme_library` が既に
存在する場合を検証する。異なるテーマの場合は light 面と dark 面が正しく
合成されることを確認する。

保有上限について、上限到達時の作成・インポート・プリセット複製が上限の扱いを
解決するまでライブラリを変更しないことを検証する。

エディタについて、ドラフトへの変更が保存操作まで永続化されないこと、破棄で
元の値に戻ること、片面の編集が反対側の面と名前を保持することを検証する。
後者は現在の欠陥に対する回帰テストとして機能する。

Deep Link について、テーマインポートの URI が通知経由の判定で受理されない
ことを検証する。確認画面で追加を選ぶまでライブラリが変更されないことも
検証する。
